## 先确认缺口

新增 `scripts/probe_debug_object_delivery.py`，只支持自身创建的无窗口目标，不接受外部 PID。监护进程先创建不带 kill-on-close 标志的原生调试对象，持有原句柄，再把副本交给已核验创建时间的工作进程。工作进程使用 NtDebugActiveProcess 附加，不调用 DbgEng，也不调用远程 break-in helper。这样在附加之前、附加完成但尚未通知监护进程时退出，原对象都仍由监护进程持有。

## 修改后的路径

采用 Python 标准库创建一个 184 字节共享缓冲区，监护进程和工作进程都持有它。**NtWaitForDebugEvent 的输出参数直接指向这块共享存储**；不是先写工作进程私有内存，再由工作进程复制给监护进程。

每次等待前，工作进程清空缓冲区；监护进程核验它为空、等待序号连续、没有已登记待处理事件，并持久化确认。工作进程收到确认后才进入系统调用。已有事件未继续时禁止复用缓冲区。正常事件处理仍保存明确的事件记录、断点修改意图和确认。

工作进程异常退出后，监护进程先通过持有的 Process 对象确认退出，再读取共享输出。严格核对状态类型、绑定 PID/TID、异常码、地址和 first-chance；部分、错误或未绑定输出拒绝。只读取事件元数据，不使用其他进程返回的句柄数值作为本进程句柄，不读取聊天正文。

恢复仍先比较实际寄存器：

- 原值仍在：不重复写寄存器。
- 确认为本次设置、且原事件仍待处理：恢复保存的原值，完整回读。
- 其他状态：拒绝恢复，不无条件清零。

之后仅对有证据的原事件执行 NtDebugContinue，再移除原调试关联。没有通过额外 ResumeThread 消耗目标的原有暂停。原状态写入表示仍受[此前实测限制](M1_DEBUG_OBJECT_RETENTION.md)约束。

这次证明的是**系统调用已返回以后**的未解析／未记录窗口。没有假定内核写入共享结构是原子的，也没有证明在系统调用内部任意时刻被终止都可恢复。
