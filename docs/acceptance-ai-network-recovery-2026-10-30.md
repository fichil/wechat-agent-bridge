# Grok 网络恢复与积压信息回补（2026-10-30）

## 诊断与边界

目标会话在 10:27 的一次记忆调用约 20 秒后出现 `ai_network_error`，自动处理暂停。旧日志没有记录底层异常类型，也没有 HTTP 响应，不能事后确定这一次是代理、TLS、连接中断还是其他传输问题。

检查时，两次不携带密钥的 xAI 模型列表请求都通过现有 HTTP 代理完成 TLS 并收到预期的 401。正在运行的后端确实继承 `HTTPS_PROXY=http://127.0.0.1:10808`，并观察到后端至该代理的 `ESTABLISHED` 连接；`NO_PROXY` 仅包含本机地址。没有修改代理设置或切换为直连。

随后通过正常重试接口尝试恢复，37 条消息的请求在约 92.5 秒后失败、未收到 HTTP 响应。其时长符合原有 90 秒读取等待上限，但旧日志未保存具体异常类型，不能把它等同于已捕获的 `ReadTimeout`。原有统一 90 秒预算明显小于 [xAI 对推理模型至少 900 秒的建议](https://docs.x.ai/developers/model-capabilities/text/best-practices)。[HTTPX 文档](https://www.python-httpx.org/advanced/timeouts/) 区分连接、读取、写入和连接池超时；它们不应在日志中合并成无法进一步诊断的一类。

## 修复

- Grok 的响应读取等待和逐块响应耗时检查采用 900 秒预算，其他服务商保持 90 秒；连接建立仍为 10 秒。
- 保留原来的有限超时、严格 JSON 输出校验、失败暂停和显式重试策略，不自动重放可能已计费的请求。
- 错误消息区分连接、读取、写入、连接池、代理、协议和系统传输问题。日志详情仅新增固定的异常分类、阶段和响应等待预算，不记录原始异常文本、请求头或密钥。
- 启动器退出宽限同步调整为 2010 秒，覆盖最慢的在途读取和来源工作进程清理；空闲服务仍立即正常停止。HTTPX 的读取超时是每次读取等待上限，逐块耗时检查不是严格的总墙钟截止，不能将 900 秒描述成绝对总耗时上限。
- 正常停止服务并备份 SQLite 后加载修复；未修改数据库结构、API 契约或原生发送源码与验收门禁。
